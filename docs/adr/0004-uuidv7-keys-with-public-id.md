# 0004 — UUIDv7 primary keys with a separate public id

- Status: Accepted (by owner on 2026-11-21, Phase 2 start plan, decision 3)
- Phase: 2

## Context

Primary keys must be safe to generate anywhere (tests, seed, application), index well under
heavy inserts, and never let clients enumerate or date users. Postgres 17 has no built-in
`uuidv7()` (it arrives in Postgres 18).

## Decision

- Every primary key is a UUIDv7 generated by the application, except `platform.outbox.id`, which
  is a `bigserial` so the relay can read in insertion order cheaply.
- Clients never see internal ids. Users are addressed by `identity.users.public_id`, a random
  URL-safe string (16–32 characters).
- Until the Phase 4 kernel provides the injected `newId`, a small tested helper,
  `apps/api/scripts/lib/uuidv7.js`, generates UUIDv7 values (RFC 9562). Its pure form,
  `uuidv7From(timestamp, random)`, makes the seed deterministic. Phase 4 may adopt it.

## Alternatives considered

- **UUIDv4:** random keys scatter B-tree inserts across the index and hurt write locality.
- **`bigserial` everywhere:** needs the database to issue ids, leaks counts and creation
  order, and makes ids guessable.
- **The `uuid` npm package:** works, but adds a dependency for about 20 lines of code.
- **A `uuidv7()` SQL function or Postgres 18:** keeps id generation out of the injected `newId`,
  and Postgres 18 is not the approved version.

## Consequences

- Inserts stay near the right edge of each index, because UUIDv7 values are time-ordered.
- UUIDv7 reveals the creation time to anyone who sees the id, which is why clients only ever
  see `public_id`.
- Tests and the seed can produce stable ids by passing a fixed timestamp and random bytes.
